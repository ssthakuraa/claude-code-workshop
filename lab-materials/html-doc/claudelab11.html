Lab 11: Enterprise Governance — Rollout Readiness, Safety Posture & Evidence

Duration: 75 minutes

Recommended Day 2 order: Lab 09 → Lab 08 → Lab 07 → Lab 10 → Lab 11 → optional Lab 12. This file is the fifth stop in that sequence, after you already have browser, API, and database verification evidence to govern.

Learning Objective

You will translate individual Codex success into something a team, architect group, or enablement owner could trust at scale. The focus is not just building artifacts. The focus is evidence, review roles, bounded safety posture, and rollout discipline.

The Key Concepts

Rollout Readiness

Enterprise adoption usually fails from weak operating discipline, not lack of model capability. A team-ready workflow needs:

  • safety posture
  • review roles
  • evidence quality
  • expansion criteria

Repo Safety Posture

In current Codex, the truthful repo-level control surfaces are:

  • .codex/config.toml
    • approval posture such as approval_policy
    • sandbox posture such as sandbox_mode
    • project-scoped integrations such as MCP

This lab should not try to recreate the old .codex/settings.json command-allowlist story. The modern repo-level safety model is bounded sandboxing, approval policy, and explicit evidence.

Enterprise Governance = Safety Posture + Review Roles + Expansion Gates

Together, these create a governance layer:

Config: approval and sandbox posture for the repo
Evidence + review: determine whether the workflow is safe to expand

Setup

Ask Codex to run these compile/build checks for you:

This is a student exercise. Stay inside the named tasks, inspect only the files this chapter explicitly tells you to inspect, and do not use `reference/` unless this chapter explicitly allows it or you need rescue help.

Run these verification checks and tell me whether both succeed:
- `cd backend && ./build-jersey-service.sh compile`
- `cd frontend && npm run build`

Client capability notes:

  • repo-managed .codex/config.toml changes are often loaded at session start, not always hot-reloaded into an already-running Codex session
  • for this lab, expect to save the config, then start a fresh Codex session from the repo root before you judge whether the safety posture is active
  • .codex/ is a protected control-plane directory in some clients; if Codex cannot edit it directly, ask Codex to draft the exact content and then apply it yourself
  • acceptable proof in a constrained client is: file state, smoke-helper output, and fresh-context verification where possible; do not pretend a missing live prompt means the repo config is absent

Exercise 1: Write the Rollout Recommendation (15 min)

Goal

Create a concise rollout recommendation for a skeptical enterprise audience.

Instructions

  1. Ask Codex to generate a short rollout recommendation:

    This is a student exercise. Stay inside the named tasks, inspect only the files this chapter explicitly tells you to inspect, and do not use `reference/` unless this chapter explicitly allows it or you need rescue help.

Write a rollout recommendation for introducing Codex into this HR repo.
It must answer:
1. who should use it first
2. what repo safety posture is safe enough for the first wave
3. what review roles are mandatory
4. what evidence is required before expansion
5. what stop conditions should pause the rollout

  2. Review the recommendation. It should be practical, slightly conservative, and tied to real observed workflow risks from the course.

Exercise 2: Define the Evidence Package (20 min)

Goal

Define the evidence package a team lead would need before approving broader use.

Instructions

  1. Ask Codex to produce an evidence checklist:

    Create an enterprise evidence checklist for this repo.
Include:
- implementation evidence
- test evidence
- browser verification evidence
- data verification evidence
- code-review evidence
- rollback or stop-condition evidence

  2. Review the checklist. Ask whether each evidence item reduces a real failure mode or just adds ceremony.

  3. Ask Codex one more question:

    Which pieces of this evidence package are mandatory before expansion,
and which are optional for a first bounded pilot?

Exercise 3: Define the Review Model (15 min)

Goal

Define the review model and bounded pilot criteria.

Instructions

  1. Ask Codex to define the review model:

    Define the review model for a bounded Codex pilot in this repo.
Name:
- learner/self-review responsibilities
- peer or senior colleague review responsibilities
- tech lead / architect review responsibilities
- the conditions required before expanding the pilot

  2. Review the model. Ask whether any role is overloaded or whether any important sign-off is missing.

  3. Discussion: What reviewer roles already exist in your organization, and which of them would actually need evidence from this workflow?

Exercise 4: Define the Repo Safety Posture (20 min)

Goal

Configure a bounded-pilot safety posture using the current Codex repo config surface.

Instructions

  1. Ask Codex about the current repo safety posture:

    Read `.codex/config.toml` if it exists and summarize the current repo safety posture.
Tell me:
- what approval policy is active
- what sandbox mode is active
- whether Playwright MCP is configured

  2. Ask Codex to draft or apply a bounded-pilot config:

    Update `.codex/config.toml` for a bounded pilot.
Preserve any existing sections already present in `.codex/config.toml`.
In this course, that most often means `[mcp_servers.playwright]` if Lab 09
already created it.
Do not invent unrelated sections such as `[features]` or `[agents]` unless
they already exist in the file you are editing.

Add or confirm:
- approval_policy = "on-request"
- sandbox_mode = "workspace-write"

Explain what those settings mean in practice for this repo.

If my client cannot edit `.codex/` directly, draft the exact TOML content for
me and tell me where to place it.

    The important point is not an old-style command allowlist. The important point is that the repo now has an explicit bounded-pilot approval and sandbox posture.

  3. Reload Codex so the repo settings are active. This is a manual learner action in the client:

    Exit the current Codex session.
Restart Codex from the repo root.
If Codex prints a `codex resume ...` command when it exits, use that.
Ask Codex to read `.codex/config.toml` and summarize the active
approval, sandbox, and MCP settings before you run the checks below.

  4. Test the posture with Codex:

    From the repo root, run these checks and tell me which ones prompted,
which ones ran, and which ones were blocked:

cd backend && ./build-jersey-service.sh test
rm -rf /tmp/some-test-folder
cp AGENTS.md /tmp/lab11-agents-copy.md

    Expected direction:

    • the in-repo build command should usually run inside the bounded pilot posture
    • destructive or out-of-repo operations should usually prompt or be blocked by the client posture

    If your environment still does not show prompts after the restart:

    • read .codex/config.toml and confirm the safety posture is present
    • record that live prompt enforcement was not observable in this client
    • continue the lab using the configured repo safety posture as the governance artifact

Exercise 5: Final Reflection (5 min)

  1. Add to AGENTS.md:

    ## Enterprise Rollout
- Start with a bounded pilot, not broad rollout
- Require explicit evidence before expanding
- Name review roles and stop conditions

## Codex Safety Posture
- Use `.codex/config.toml` for repo approval and sandbox posture
- Keep a bounded pilot on `workspace-write` plus `on-request` until the evidence is stronger
- Re-verify the repo posture from a fresh session before you trust it

  2. Reflect: The three governance layers are now in place:

    • Repo safety posture (this lab): approval policy and sandbox mode in .codex/config.toml
    • Evidence + review (this lab): bounded rollout discipline
    • Verification stack (Labs 08-10): tests, browser checks, and data checks

Success Criteria

Key Takeaways

  1. Enterprise rollout needs bounded scope; start with a conservative pilot, not a broad mandate.
  2. Current Codex repo safety is expressed through approval_policy, sandbox_mode, and explicit verification, not the old settings.json command-allowlist story.
  3. Stop conditions matter; if you cannot say what pauses expansion, the rollout is not ready.
  4. Governance is architecture work, not admin overhead added after the fact.
